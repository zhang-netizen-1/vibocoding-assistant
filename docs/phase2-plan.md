# 二期计划：统一条目内容、口语搜索、验收要求

依据：`docs/prd-design-knowledge-site.md` v1.4 第 4.1、4.3、6、7、11、12、16 节；`docs/phase1-plan.md`。
分支 `phase2-aliases`（从 main `8e79e63` 拉出），工作目录 `~/Downloads/vibocoding-phase2`。条目总数保持 187。

## 规则（同一期）

1. Codex 在 Mac 上做；它的沙箱写不了 git，所以每步交补丁和提交脚本，由 Grok Bot 审过后提交。
2. 站内链接一律相对路径（站点在 `/vibocoding-assistant/` 子路径下）。
3. 验证只用无界面浏览器；不用电脑操作工具、AppleScript、`open`，不碰用户的真实 Chrome。
4. 不合并、不推送 main、不发布；不碰主仓库里用户未跟踪的文件。
5. 内容规则：
   - **别名**：每条 3–10 个，是中国设计师真会打进搜索框的说法：口语描述（「浮起来」「小黑框」）、其他产品/设计系统的叫法（Toggle / Switch、Dialog / Modal、Snackbar）、常见近义词和错别字。不写营销词，不写和别的条目更贴切的词（一个口语只指向最该指向的条目）。
   - **验收要求**：每条提示词 3–6 条。每条要么有数字（对比度 ≥ 4.5:1、时长 ≤ 400ms、点击区 ≥ 24×24px），要么有明确判据（「屏幕变宽时绝不能反而变少列」「连点时不出现叠影」）。不写「好看」「流畅」「合适」。来源优先级：测评失分项 → 无障碍底线（对比度、焦点、点击区域、减弱动态）→ 不跳动、不溢出 → 该条目最容易做错的点。与 PRD 第 15、16 节的数值一致。测评结论：**写进去的稳定，没写的每次会变**，所以最容易变的点要写成数字。
   - **提示词**：默认「改现有页面」版（先找到项目里已有的对应部分 → 改成什么 → 沿用现有颜色字体间距 → 不改无关内容 → 验收要求 → 完成后列改动文件并逐条说明怎么验证）；「新做一个」版折叠，以现有提示词为底。两版都带同样的验收要求。不绑定某个 AI 工具。专业词后括号附白话。
   - 按钮条目照 PRD 6.2 原文升级（含测评第 2 轮的 5 条验收要求）；网格、交叉淡化也用测评得出的失分点。

## 数据结构

- 新增 `site-src/content/<栏目>.json`，按条目 slug 存放编辑内容：`aliases`、`when_use`、`when_avoid`、`params`（关键参数，可空）、`prompt_edit`（改现有页面）、`prompt_new`（新做一个）、`acceptance`（3–6 条）。
- `entries.py` 把编辑内容叠加到一期的统一条目上；原有来源文件（UI HTML、动效 JSON、指南、技能目录）不改，旧提示词保留作对照。
- 构建时严格校验：187 条每条字段齐全、别名 3–10、验收 3–6，缺一条构建失败。

## 风险

| 风险 | 对策 |
|---|---|
| 内容量大、Codex 写得空泛 | 先样本 10 条定标准，按栏目分批；Grok Bot 每批抽查数字、判据、口语是否像真人说的 |
| 提示词变长让 AI 更慢（测评实测约 2 倍） | 验收 3–6 条，只写真正会错的点 |
| 别名把搜索带偏（一个口语命中太多条） | 50 条查询测试表兜底；冲突的口语只留给最贴切的条目 |
| 动了一期页面 | 宽松模式下未填条目页面逐字不变；最后全量回归 |
